OpenDMD HTTP API#

Everything the web app does goes through this API, and a script can do the same. The source of truth is firmware/src/http.rs. In the examples $DMD is the display's address.

DMD=http://opendmd.local
curl -s $DMD/api/status

Ground rules#

  • Plain HTTP. Anyone who can reach the display can change its settings, delete files and rewrite its firmware, unless an API key is set (see "Security"). Keep it on a trusted network; never forward a port to it.
  • JSON in, JSON out. Bodies are JSON unless a route takes raw bytes, with Content-Type: application/json (415 otherwise; curl --json sets it). Every error is a non-2xx status with {"error":"<why>"}, except what the HTTP server refuses before a route sees it (405 for a route that exists for another method, a malformed request, too long a URI or header): those are its own text/html.
  • Names ad blockers leave alone. A path named like analytics (stat, track, log) is on EasyPrivacy, and uBlock Origin and Brave then fail the web app's request as a network error. make blocklist-check (tools/blocklist-check.py) tests every route against EasyPrivacy and EasyList; a new route must pass it.
  • Size limits. JSON bodies ≤ 8 KB (413 over), the schedule ≤ 2 KB, a web app pack ≤ the www partition (786,432 B in table v4). Uploads are streamed, any size, but no data for 5 s, or 120 s in all, is a 408. A body needs a Content-Length.
  • One thing at a time. One server task, at most 7 open connections (HTTP_MAX_SOCKETS). Transfers and the listings (/api/files, /api/cache/list, /api/cache/failed) run one at a time, two more waiting; with both places taken, a GIF, a prepared copy or a listing gets 503 + Retry-After: 1 at once, a web app file, a playlist or a Formula file after 1 s (at once while an upload is in hand). Short of memory, a listing or transfer is refused up front: 503 + Retry-After: 2. So is any request with a body (a settings change, a play, a schedule, a Formula sent to the panel) when the heap has too little free, or no single block big enough for the body, just then (net.heavy_refused counts them): nothing was done. Retry after the delay; do not fire requests in parallel.
  • Slow commands. A playlist change waits up to 60 s for the index rebuild, a WiFi scan 12 s, a Follow test 20 s, then 504; a play, pause or Previous not taken within 0.8 s is a 503 + Retry-After: 1, and one taken but not done within 0.7 s more a 202 ("pending":true); playback not running, 503.
  • Paths are card-absolute (/gifs/Consoles/SNES_Super_Metroid_01.gif), percent-encoded in URLs; one that leaves the card is a 400.

Fields that recur#

Commands that touch the playlist answer with what the display now has:

field meaning
entries number of entries in the playlist in play
index "loaded" (the index on the card was current), "built" (rebuilt now), "in-ram", or null (the playlist was not touched)
index_ms how long opening or building the index took, ms
overrides per-GIF overrides resolved into the playlist

overrides is the rebuild's count: with index null it is 0 whatever the playlist has (GET /api/status carries the playlist's own).

A playlist name (set): "" is /filelist.txt, filelist.<x> is that file at the root, any other name is /sets/<name>.txt. No / or ...

Playback#

POST /api/play#

Play one file now (with the transition, from its prepared copy if there is one), then the playlist carries on.

Body: {"path": string}, a card-absolute GIF path, a Formula (a bundled one by name, @formula:<stem>; one of yours on the card, /formulas/<stem>.psi, maybe with ?a=…; or inline, @formula?psb=…) or a virtual file (see "Virtual files"). "live":true: only replace a formula on screen (409 if none is; 400 for any other path). "over":true with a formula: draw it over the file on screen instead of playing it, until the playlist moves on to another file (in place of the look_formula meanwhile); with "live" it changes that formula (409 once the playlist has moved on); "path":"" takes it off. "over" takes only a formula or "" (a card .psi path must still be card-absolute); with no playlist running it is a 503; a formula that covers the GIF entirely (it reads none of ur ug ub ul and nothing shows through it) or is too heavy to draw over GIFs is a 400 with the reason.

A Formula played this way (not "over") stays as long as formula_keep says: one turn of the dwell (the default), a minute, five, or until something else plays (another /api/play, /api/skip or Previous, a playlist change). A live edit keeps it kept. While it is kept, /api/status now_playing.kept_s says for how long (0: until changed).

Reply: {"ok":true,"path":"…"} (with "over":true when drawn over).

Errors: 400 neither card-absolute nor a Formula, or a bad formula (path must be card-absolute and stay on the card, or a Formula (@formula…)); 404 the file does not open, or no bundled Formula has that name (the path, cut to 96 bytes, then : there is no bundled Formula by that name; what was playing carries on); 415 not a GIF, a virtual file this firmware does not know (@nonsense), a retired @clock/@text path (the clock and the scrolling text are gone: play a Formula (a clock is one, @formula:big-clock)), or a retired @fx: path: the built-in effects are gone (the built-in effects are gone: Formulas replace them (play one as @formula?psb=…)); 503 no playlist running; 413 body over 8 KB, or an inline formula over 6,144 B (send a longer one as POST /api/play/formula); 501 a Formula (any of the three forms, or "over"/"live") on a build without Formulas (/api/status features lacks "formulas"): {"error":"Formulas aren’t in this firmware build"}.

curl -s $DMD/api/play --json '{"path":"/gifs/Consoles/SNES_Super_Metroid_01.gif"}'
curl -s $DMD/api/play --json '{"path":"@formula:big-clock"}'

POST /api/play/formula#

Show a Formula now, whatever its length: what the web app's Show on panel and its live edits send. The body is the compiled Formula itself (Content-Type: application/octet-stream exactly, 415 otherwise; the bytes pkg-psi's program(src) or psi build makes, 16,384 B at most, 413 over), not a path. Query: live=1 and over=1 as "live"/"over" for /api/play, and the sliders a=, b=, c=, fps= as on an @formula path.

The display holds it in memory, one at a time, and plays it as @formula:~sent[?a=…] (that is now_playing.path; the title is its name line, else "Formula"). Each one sent replaces the last (whose memory goes before the new body is read), and it is let go once the panel moves on to anything else; it is not kept in Recently played, and it can't be the look_formula (400). Once let go, @formula:~sent is a 404 (the path, then : that Formula is no longer on the panel: show it again). Nothing touches the card, but a playlist must be running: with none (as without a card) it is a 503 (no playlist is running).

Reply and errors as /api/play (409 a live edit after the playlist moved on, 400 a formula that does not load, 503 no playlist), and 503 + Retry-After: 2 when the heap has no room for the body just now, or Retry-After: 1 when the display has none for the program or its canvas (retry then); 501 on a build without Formulas.

psi build my.psi -o my.psb
curl -s "$DMD/api/play/formula?a=0.4" -H 'Content-Type: application/octet-stream' --data-binary @my.psb

Waiting on the display#

The play, pause, Previous and panel-test requests are done by the display between frames (the ones that apply settings too, answered as long requests: see GET /api/job). If it has not taken the request within 0.8 s (a frame held up on the card, say) the answer is 503 with Retry-After: 1 and nothing is done (net.player_busy); ask again. A play, pause or Previous it has taken but not finished within 0.7 s more is answered 202 {"ok":true,"pending":true}: it is under way, and /api/status shows the result.

GET /api/job#

The answer to a long request. PUT /api/config, /api/schedule, POST /api/wake, /api/reindex, /api/follow/test, GET /api/wifi/scan and /api/name-check are answered at once if they are done within 0.3 s; otherwise 202 {"pending":true,"job":N} with X-Job: N and Retry-After: 1, and GET /api/job?id=N gives the request's own answer once it is there (202 again until then, 504 once the request's own limit has passed; 404 for no such job: answered already, or dropped to make way for another long request after 5 s without a poll). One long request at a time: another while one is pending is a 503 + Retry-After: 2. The web app follows these by itself (source.js req).

curl -s -X POST $DMD/api/reindex -D - | grep -i x-job
curl -s "$DMD/api/job?id=1"

POST /api/pause#

Toggle pause. Reply: {"ok":true,"paused":bool}, the new state.

While paused the panel holds its frame and the display lets go of the file (its memory goes to preparing copies and downloads), so resuming brings in the next entry, with the transition, from the held frame.

curl -s -X POST $DMD/api/pause

POST /api/skip#

Move on to the next entry now. No body. Reply: {"ok":true} (at once; the skip happens on the display's next frame).

?back=1 is Previous: play the recent entry one older than the one on screen (again: older still) as /api/play does; 404 at the oldest.

curl -s -X POST $DMD/api/skip
curl -s -X POST "$DMD/api/skip?back=1"

Status and health#

GET /api/events#

What the Now page shows, pushed: Server-Sent Events (text/event-stream, retry: 3000), one data: line of JSON per event, sent when what it says changes and at least every 3 s (the state is looked at four times a second). The clock, the position in the file and a Formula's figures do not count as a change (a file's first frame being up does), so a quiet stream sends one event every 3 s: a client that hears nothing for longer than that, say 10 s, can take the stream for dead.

curl -sN "$DMD/api/events"

retry: 3000

data: {"t_ms":57784,"now_playing":{"ordinal":12,"path":"/gifs/Arcade/ARCADE_Rockman2_08.gif","title":"Rockman2","elapsed_ms":2716,"frame":46},"paused":false,"entries":10162,"manifest":"/sdcard/filelist.txt","index_state":"ready","brightness":96,"sd":{"mounted":true,"readable":true,"attempts":1,"error":null,"formatting":false},"mode":"normal","mode_until":null,"wake_until":null,"schedule":{"rule":null,"set":null,"until":null},"context":{"source":"replayos","enabled":false,"state":"off","system":null,"platform":null,"console":null,"game":null,"matches":null,"since":null,"seen":null,"step":null,"error":null}}

The fields are GET /api/status's of the same name (t_ms the display's clock as the event was made, now_playing.elapsed_ms the position at that moment, now_playing.formula while a Formula plays), with brightness the setting (GET /api/config), sd only {mounted, readable, attempts, error, formatting}, and context.since always null. For anything else, and for recent, read the status.

At most 2 listeners at once; another is a 503 with Retry-After: 5. A listener that stops reading is not waited for: events that do not fit are skipped (the latest goes once it can) and after 5 s the connection is closed (net.events). No event is made while the heap is short (under 10 KB free, as for a status read); the next one goes when there is room. Firmware before 1.0.0 may not have the route (a 404): poll the status.

GET /api/status#

A cheap snapshot; counts since boot. ?now=1 is the slim one the web app's Now page polls between full reads where it has no event stream (~300 B, one segment): uptime_secs, t_ms, now_playing, paused and transfer only.

Sent chunked (Transfer-Encoding: chunked), written out as it is made; a client polling faster than every 100 ms gets the last answer again, sized. With under 10 KB of heap free it is a 503 with Retry-After: 1 (net.status_refused).

Settings#

Where they are kept. The settings that belong to what plays travel with the card, in /opendmd.json at its root: brightness and its ceiling, dwell, shuffle, platforms, the playlist (set), the time zone, the schedule, transition, auto_prepare, Follow RePlayOS on/off and its host, attract, look, glow, look_formula, boot_show, boot_formula, panel_sync, panel_split, formula_jit, formula_arena, formula_keep, beta_updates, network. A change is on the card the moment it is saved, whatever plays. The device keeps the rest itself, never on the card: the WiFi details and name, the location (lat, lon), the API key and the RePlayOS code (secrets), the card's clock and its slow-clock record, and the panel timing. The location is never in /api/status or a link either. It also keeps a copy of everything, what it runs on until a card is read and with no card at all.

The file is JSON, by the names below, sealed with a last member "crc"; it is saved as opendmd.json.new, then the old one becomes opendmd.json.bak and the new one takes its name, so a power cut leaves the old settings or the new. It may be edited on a PC (the seal is then ignored): a value the device would refuse over the API is kept as it was, with a log line. A card from another display brings its settings; this display's WiFi and secrets stay. A card without the file gets one, from the settings in force, when it is first read. Copying the pack onto a card, or formatting it, leaves no settings file: the next boot writes one.

Formulas compiled on the display#

Each card Formula, /formulas/<stem>.psi, plays from its compiled file beside it, /formulas/<stem>.psb (what the web app writes when it saves one, or psi build). Once the display has mounted a card and started playing, it checks the folder in one pass and compiles, one at a time in the background, every .psi whose .psb is missing, older than its .psi (FAT's 2 s stamps) or for another version of the compiled format (psi_abi: the headers are read only when the version may have changed since the last check, which /formulas/.psb-abi records). Until one is ready a playlist skips it and a look or start-up show of it is not drawn; a look is built again once its .psb is written. The .psb is given the .psi's date, so it stays current until the source changes. A source that does not compile is marked (its .psb holds the mark, which plays as "this Formula does not compile") and not tried again until it changes. A compile the memory cannot hold, or one a busy card put off, is tried again later: a finite number of retries (20, 30 s apart, with WiFi off; 2, 60 s apart, with it on; 2 s apart right after one that compiled), one compile each, the memory ones only once the heap has room; failing that, at the next start. A compile holds the card as a file transfer does: the playback cache's builder waits for it. A .psb refused where it plays (damaged, or another version's) is prepared again: by the next retry if one is due, else at the next start. While a .psb is being written, a PUT, DELETE or move of that Formula (or of /formulas itself) waits for it, up to 1 s, else 503 "the display is preparing this Formula; try again in a moment" (nothing done: ask again). It happens whether or not the network is on. The log has a line for each and a summary; the counts are /api/status card_formulas, set after the first pass and after each retry.

{"set","playlist":"/filelist.txt","overrides":[{"path", "w"?, "dwell"?, "dwell_x"?, "loops"?}]}

w weight (Favourite 3, Play less 0.5); dwell seconds, or dwell_x times the usual; loops. To change them, write the .meta beside the playlist (/sets/<name>.meta, /filelist.meta), a line per GIF: its path, then tab-separated w=<n>, dwell=<s> or dwell=<k>x, loops=<n> (anything else on the line is skipped, as earlier firmware's never now is: that GIF plays again).

curl -s "$DMD/api/overrides?set="
printf '/gifs/Consoles/SNES_Super_Metroid_01.gif\tw=3\n' > filelist.meta
curl -s -X PUT --data-binary @filelist.meta $DMD/api/files/filelist.meta

GET /api/schedule#

The schedule as saved, or {"rules":[],"night":null}.

curl -s $DMD/api/schedule

PUT /api/schedule#

Replace the schedule (≤ 2 KB, at most 16 rules):

{"rules":[{"days":[],"from":"00:00","to":"00:00","set":"filelist.hall","dates":["10-01","10-31"]},
          {"days":[1,2,3,4,5],"from":"18:00","to":"23:00","set":"consoles","brightness":96}],
 "night":{"from":"23:30","to":"07:00","mode":"off","brightness":8}}

days 1 (Monday) to 7 (empty or absent: every day); dates the first and last day of the year it runs, "MM-DD", inclusive, wrapping over New Year when the last is earlier (["12-27","01-06"]; absent: every day of the year); set and brightness optional. The first matching rule wins; to ≤ from runs past midnight (and belongs to the day and date it starts), to = from is the whole day. night (every day, beats every rule) has mode "off" (panel dark) or "dim" (at brightness, default 8). With "sun":true it runs from sunset to sunrise at the saved location (lat/lon in /api/config) instead of from–to (which may stay, unused), starting offset minutes after sunset and ending as long before sunrise (−180 to 180, default 0; negative: before sunset, after sunrise); without a location it stays off. Status mode_until is then when it ends (null in a polar night). Rules change what plays, not the saved settings. Nothing applies before the clock is set from the network.

Reply: {"ok":true,"rules":N,"night":bool}. Errors: 400 a bad time, day, date, mode, offset or playlist name (the message names the rule); 404 set not found: <names>; 413 over 2 KB.

curl -s -X PUT $DMD/api/schedule --json '{"rules":[],"night":{"from":"00:00","to":"07:00","mode":"off"}}'

POST /api/wake#

Suspend the schedule for a while (normal mode, the saved playlist): {"minutes":N}, 0..=1440; 0 resumes it now. Reply: {"ok":true,"minutes":N,"wake_until":"HH:MM"|null}. 400 over 1440.

curl -s $DMD/api/wake --json '{"minutes":60}'

Prepared copies#

A prepared copy is a smaller GIF the display plays in place of the original. The display makes them itself while the panel is dark or paused (auto_prepare; always adds a slow drip while a prepared GIF plays); the web app makes them faster and uploads them to /cache/<Category>/<xx>/<name>.gif (docs/cache-format.md).

GET /api/cache#

How many of the playlist's files are prepared:

{"total","prepared","state","count_ms","auto"}: the playlist's length; how many have a copy or play as they are (null until counted); "counting" or "ready" (poll until ready); the last count's ms. auto, the display's own preparing: {"mode","state","reason","policy","session","failed","avg_full_s","avg_drip_s","eta_s","current"}: mode = auto_prepare; state idle, running, paused, done; reason it is not running (off, playing, gif on screen (an original plays), late frame (held off a while after a visibly late frame), low memory, busy, transition, reindex, no playlist, card error); policy full or drip (pace); session copies since boot; failed GIFs it cannot prepare; avg_*_s s per file per pace; eta_s s left at the full pace; current the GIF in hand.

curl -s $DMD/api/cache

GET /api/cache/list#

Every prepared copy, streamed: {"paths":["/cache/…"],"count":N}. Subtract it from a playlist for what is left to prepare.

curl -s $DMD/api/cache/list | jq .count

GET /api/cache/failed#

The GIFs with no copy, streamed: [{"path":"/gifs/…","reason":"image truncated"}], [] if none. Reason more than 256 colours…: it plays as it is (done).

curl -s $DMD/api/cache/failed

POST /api/cache/failed#

Record a GIF the browser could not prepare either (or one that plays as it is), so the display skips it too: {"path":"/gifs/….gif","reason":string} (kept to one line, ≤ 200 characters). Reply: {"ok":true,"path","added":bool} (false: it was there). 400 not a /gifs/….gif path.

curl -s $DMD/api/cache/failed --json '{"path":"/gifs/Other/broken.gif","reason":"image truncated"}'

DELETE /api/cache/failed#

Forget the whole list, so replaced GIFs are tried again. Reply: {"ok":true,"cleared":bool} (false: none).

curl -s -X DELETE $DMD/api/cache/failed

POST /api/cache/forget#

Delete one GIF's prepared copy (after replacing the GIF): {"path":"/gifs/….gif"} (on the panel, the display moves on first). Reply: {"ok":true,"path","removed":bool}. 400 not a /gifs/….gif path.

curl -s $DMD/api/cache/forget --json '{"path":"/gifs/Consoles/SNES_Super_Metroid_01.gif"}'

Follow RePlayOS#

With follow on, the panel follows a RePlayOS box: the game's art while a game runs, the attract playlist in the menus (attract is always "" now). Set with PUT /api/config (follow, follow_host, follow_code, attract_set, attract); its state is /api/status context.

POST /api/follow/test#

Ask the box for its version and status, saving nothing: {"host"?: string, "code"?: string} (absent: the saved ones; an empty body is fine). Up to ~20 s. The saved code goes only to the saved host: a host that is another one needs its own code (400 without, when a code is saved). Likewise PUT /api/config with a new follow_host and no follow_code forgets the saved code.

Reply: {"ok","reachable","version","status","view","system","game","error"}; status is the box's HTTP status (401: wrong code). An early failure has only ok, reachable, error (and version).

curl -s $DMD/api/follow/test --json '{"host":"192.168.1.20","code":"1234"}'

Network#

The display joins the WiFi network in its settings. With none, or after failing to join twice, it raises an open network, OpenDMD-Setup, as a captive portal (unknown paths redirect to /), and restarts every 10 minutes to try again. While it is the setup network, only setting up WiFi answers: /, /setup, the probes, GET /api/status, GET /api/config, PUT /api/config (wifi_ssid, wifi_pass, wifi_eap_user, wifi_eap_identity, wifi_eap_ttls, hostname, api_key only; anything else in the body is ignored), GET /api/wifi/scan and POST /api/reboot. Every other route and card file is a 403; any other page redirects to the setup page.

method path what
GET / the web app (in setup mode, the setup page; the web app is at /index.html there)
GET /setup the built-in setup page: join a network
GET /hotspot-detect.html, /generate_204, … captive-portal probes: a redirect to / in setup mode, else 404

Over USB, the browser installer sets it with Improv Serial instead (the display joins at once, no reboot). Over HTTP, set the network with PUT /api/config, then reboot:

curl -s -X PUT $DMD/api/config --json '{"wifi_ssid":"MyNet","wifi_pass":"secret"}'
curl -s -X POST $DMD/api/reboot

A work or school network (WPA2-Enterprise, 802.1X: eduroam, a company's WiFi) needs a username as well, wifi_eap_user, with its password as wifi_pass; "" as the username goes back to a network with a password alone. The display answers PEAP or TTLS, whichever the network asks for (PEAP with MSCHAPv2 inside, TTLS with wifi_eap_ttls, MSCHAPv2 unless the network says otherwise). The RADIUS server's certificate is not checked: the display accepts any server (no CA certificate is kept, so the TLS runs without verification). A fake access point with the same name could take the login (and the MSCHAPv2 exchange can be attacked offline), so use a password for this device alone where the network offers one. Also not done: EAP-TLS (a client certificate) and WiFi details over USB (Improv sends a name and a password only: a save over USB clears the username).

curl -s -X PUT $DMD/api/config --json '{"wifi_ssid":"eduroam","wifi_eap_user":"ab12@example.edu","wifi_eap_identity":"anonymous@example.edu","wifi_pass":"secret"}'
curl -s -X POST $DMD/api/reboot

Security#

This keeps out casual use (a guest, a script, another web page in your browser), not someone on the same WiFi: it is plain HTTP. The key is the only lock, and it travels in clear text on your network.

  • Host. Every request, GET included, must name the panel in its Host header: opendmd.local, <hostname>.local (or the name mDNS answers to after a clash; after a rename, the old name too until the restart), the bare names, the panel's current IP address, or localhost/127.0.0.1 (any port). Anything else is a 421 ("this panel answers only to its own names"; in setup mode a GET is sent to the setup page instead): a web page whose DNS name was pointed at the panel (DNS rebinding) cannot use it. A request with no Host (HTTP/1.0) is fine. Reach the panel by one of those names; a name your router hands out (opendmd.lan) is refused.
  • A POST/PUT/DELETE whose Origin is another host than its Host is a 403 (no Origin, as from curl, is fine).
  • API key (Settings → Device → Security; the web app shows a banner while there is none, and /setup offers one): with api_key set (PUT /api/config, 8..64 of A-Z a-z 0-9 . _ ~ -, "" = off; GET shows api_key_set), the API and the card's files (/gifs/, /cache/, /sets/, /formulas/, /filelist*) need Authorization: Bearer <key> or ?key=<key>, else 401. Not the web app's files or /setup, nor in setup mode (OpenDMD-Setup), where a lost key can be cleared (and only the WiFi set up: see "Network"). ?key= is for curl: a browser keeps it in its history; the web app sends the header. The panel never logs it.
  • Headers. The web app's files and /setup carry a Content-Security-Policy (frame-ancestors 'none': never in a frame) and X-Content-Type-Options: nosniff. A card file goes out as the image it is (image/gif, png, jpeg, webp) or as application/octet-stream with Content-Disposition: attachment, never as HTML or SVG, always with nosniff and Content-Security-Policy: sandbox; default-src 'none': a file anyone wrote to the card never runs as a page of the panel's.
  • Updates are signed. PUT /api/firmware and PUT /api/www take only what the release key signed (docs/ota.md, docs/www-pack.md).
K='Authorization: Bearer <key>'
curl -s -H "$K" $DMD/api/status
curl -s -X PUT $DMD/api/config -H "$K" --json '{"api_key":""}'

Web app update#

The web app is one file in the display's flash, a www pack (docs/www-pack.md): opendmd-web/www.pack from make web, dist/opendmd-<version>-www.pack in a release. Served at /… and /www/….

GET /api/www#

{"version","bytes","entries","ok","error","staged"}: the pack's version (git describe of its build), size, file count, whether it verified, why not (erased, damaged, an update cut short, being written), whether this boot's last update was staged on the card (true, or null: none, or refused at its header).

curl -s $DMD/api/www

PUT /api/www#

Write a new pack (the whole file): a release's, signed with the release key (docs/www-pack.md "Signature"). Its header is checked before anything is erased: not a pack, an unknown format, or a length not the body's is a 400 at once, an unsigned pack a 422 at once, and the app in flash stays. With a card, the pack is staged there and read back (size, CRC, the signature; failed reads retried): a 408 (cut short), 422 (bad CRC or signature, or a key this display does not know), 500 (unreadable) or 503 (the signature could not be checked just now: retry) leaves the old app. Then it is written to flash (a few seconds for ~0.5 MB) and served at once, no reboot. If that write fails (500), pages are 503 and the next restart writes the pack from the card, or push again. Without a usable card it is a 503 (a pack is staged on the card, as a firmware update is), and the app in flash stays.

Reply: GET /api/www's object. 411 no length; 413 too big. Any signed pack is accepted, older or newer: check the version GET /api/www reports (make www-push HOST=… signs a local build with FW_SIGN_KEY and does).

curl -s -X PUT --data-binary @dist/opendmd-1.0.0-www.pack $DMD/api/www
curl -s $DMD/api/www

Firmware update#

A signed bundle (dist/opendmd-<version>-<variant>.odfw, make fw-release) is staged on the card (one is needed), checked and installed (docs/ota.md); make fw-ota HOST=… does it.

GET /api/firmware#

{"version","build","variant","layout","features","flash_size","flash","updater","pending","last","log"} (features, layout as in /api/status): the running version (a bundle's, and /api/status's; build its image descriptor, "<version> <variant>"), the flash layout it is built for (variant: 4mb) and the flash chip's real size in bytes (flash_size; a board with more flash reports its own size), the clock and read mode the flash runs at (flash: {"mhz": 40|80, "mode": "dio"|…}, read back from the chip), the updater in flash (updater: {"version": "updater 2", "panel": true}, its app descriptor's version, or null for version if it cannot be read; panel: it shows "Installing" on the panel while it installs, which only an updater from a USB install of 1.0.0 or later does, since an update over WiFi never replaces the updater), a staged update not yet installed (or null), the last non-blank line of the card's /update/log.txt (last, ≤ 200 characters) and its last ≤ 1 KB of whole lines (log, the firmware's and the updater's; both null without a card or log).

curl -s $DMD/api/firmware

PUT /api/firmware#

The bundle as the body (411 no length, 413 too big). Header, the flash layout (the bundle's must be the display's variant and partition table, layout: a bundle for a newer table says to reinstall over USB from opendmd.dev/install; one for an older table says to use a release made for the display's layout; any other ODFW magic, such as an 8mb bundle from 1.0.0-beta.16 or earlier, is for another flash layout and refused in words), size, SHA-256, Ed25519 signature and the image's app descriptor are checked: a failure is a 422 with the reason, nothing staged; cut short 408; no card 503. Another key's bundle, or one for another layout, is refused once the 140-byte header is in; the key the image's key trailer names must be the one that signed it. Any validly signed bundle is accepted, older ones too, unless the firmware was built with a rollback floor (docs/ota.md). Then {"ok":true,"version":"…","rebooting":true}. From the accepted header the panel shows a still message instead of what plays ("Updating", the version, "Don't unplug"; "Installing" once the bundle is staged), and now_playing.path and .title are empty meanwhile; a refused or cut-short upload takes it down and playback resumes (a paused file's frame, and its name, come back). The panel keeps "Installing" while the updater installs (~45 s from the restart to playback, dark only for a moment at each restart) when the updater lights it (updater.panel in GET /api/firmware); with an older updater the Installing screen says "Dark while it installs" and the panel is dark until playback. The new firmware's first boot says "Updated to v" in the start-up show's status line for 3 s (the show runs 3.9 s, or 6.85 s full; with boot_show off, the short show for that boot).

curl -s -X PUT --data-binary @dist/opendmd-1.0.0-4mb.odfw $DMD/api/firmware

Virtual files#

Paths beginning with @ are drawn, not read from the card: for POST /api/play, a playlist line. Options follow ? as key=value pairs joined by &; unknown keys and bad values are ignored (the default stays).

@formula — a formula (the app's Formulas), compiled: the display never compiles. psb=<the compiled Formula, base64url, no padding> (what the web app's pkg-psi program(src) makes, or psi build), a=, b=, c= (sliders), fps=50|100|25 (default: the formula's fps line, else 50; as a look over the GIF the line is not used). A heavy one is shown at fewer frames a second; one estimated over 40 ms a frame on the VM (32 ms at fps=100), with no JIT and no still cache, is a 400 (this formula is too heavy for the panel …), however fast the JIT would draw it; status now_playing.formula has frame_us, frame_ms, asked_ms, beam_us (the raced frame time on the panel's refresh, µs; 0 while its frames are not raced, see scan.beam), compile_us (the load's time, µs), still (the still cache's bytes) and jit: {"on":true,"bytes":N} while the JIT's kernel (N bytes of code) draws its pixel stage, else {"on":false,"why":"…"} (e.g. off (setting), being checked, the VM is faster for this formula, no executable memory, too many values for the kernel, not in this build), and render_us_total/renders: the playing formula's render µs in all (wrapping) and renders since boot, whose differences give a stretch's exact mean (frame_us is a running mean of the last few frames). The whole inline path is at most 6,144 B (a longer Formula is sent as bytes: POST /api/play/formula, @formula:~sent); name=<url-encoded> (≤ 60 characters) is its name for display.

By reference (what playlists and the look use, so a Formula's length never matters there): @formula:<stem>[?a=&b=&c=&fps=] plays a bundled Formula (its file's stem in opendmd-web/formulas/, for the files there with a -- bundle line, compiled into the firmware: endless-road, big-clock, …); a card path ending .psi, /formulas/<stem>.psi[?a=…], plays one of the user's from the compiled file beside it, /formulas/<stem>.psb (16 KB at most), which the web app writes whenever it saves the .psi. A name that is not bundled, or a Formula with no compiled file, is a 404; one compiled for another version of the firmware is a 400 (/api/status psi_abi is the version this display takes; the web app prepares its Formulas again for it). Its title is the compiled Formula's name (its name "…" line).

curl -s $DMD/api/play --json "{\"path\":\"@formula?psb=$(psi build my.psi --base64)\"}"
curl -s $DMD/api/play --json '{"path":"@formula:endless-road"}'
curl -s $DMD/api/play --json '{"path":"/formulas/my-road.psi?a=0.4"}'

Retired: @clock, @text. The clock (@clock…) and the scrolling text (@text?msg=…) are gone: a Formula draws a clock (@formula:big-clock). POST /api/play answers 415 for either. In a playlist such a line is skipped as the playlist is read, with an info-level log line (playlist: skipping "…": the clock and scrolling text are gone (a Formula draws a clock)); the rest of the playlist plays.

Retired: @fx:. The built-in effects (@fx:tunnel, @fx:rotozoom, @fx:starfield, @fx:wire) and the old Formula path @fx:psi?src=… are gone: they are Formulas now. POST /api/play answers 415 for any @fx: path. In a playlist (/filelist.txt, /sets/*.txt) such a line is skipped, with one log line each time the playlist is read (playlist: skipping "<line cut to 48 chars>…": the built-in effects are gone (Formulas replace them)); the rest of the playlist plays.

@boot — the start-up show. len=short|full|card|updating|installing (card: the status card; updating, installing: a firmware update's still message, 2 s), and for it v=<version>, ip=<address>, ap=<network>, note=<text> (≤ 32 characters each), up=1 (the first boot of a new version: "Updated to v"). formula=<path> (URL-encoded; a bundled Formula by name or an inline one, as boot_formula holds them) plays the show with that Formula in the wordmark's place, the frames the panel draws at start-up: the line over it only when there is something to say. One that does not build, or a Formula on the card (the panel reads those from the card at start-up, not from a path), plays the wordmark. The path may then be as long as a Formula's (6,144 B).

curl -s $DMD/api/play --json '{"path":"@boot?len=full"}'
curl -s $DMD/api/play --json '{"path":"@boot?len=short&ap=OpenDMD-Setup&formula=%40formula%3Astarfield"}'

Also @power-on (the power-on effect) and @card:<title>|<subtitle> (a title card, 3 s).
